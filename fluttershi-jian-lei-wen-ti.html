1. 首页多接口如何组织 Bloc 与 Repository

场景

一个首页同时展示：

HomePage
 ├─ 用户信息
 ├─ 车辆信息
 └─ 消息列表

三个接口互相独立，但页面需要同时展示。你会怎么设计 Bloc、Repository 和页面状态？

参考答案

不建议在 HomePage 中直接写三个 Dio 请求，也不建议无脑做一个巨大的 HomeRepository.getAll() 把所有业务绑死。

可以根据业务生命周期拆成：

HomePage
   │
   ├── UserBloc ─────→ UserRepository
   │
   ├── VehicleBloc ──→ VehicleRepository
   │
   └── MessageBloc ──→ MessageRepository

如果三个数据确实构成明确的“首页聚合业务”，也可以：

HomeBloc
   │
   ├── UserRepository
   ├── VehicleRepository
   └── MessageRepository

关键不是“一定几个 Bloc”，而是看：

  • 业务边界；
  • 状态生命周期；
  • 是否存在独立刷新；
  • 是否会被其他页面复用；
  • 失败是否需要独立处理。

继续追问

三个请求里一个失败了怎么办？

不建议只有：

Loading
Success
Failure

更合理的是支持部分成功：

class HomeState {
  final User? user;
  final Vehicle? vehicle;
  final List<Message> messages;

  final LoadStatus userStatus;
  final LoadStatus vehicleStatus;
  final LoadStatus messageStatus;
}

判断候选人水平

一般：

Future.wait 三个接口，然后 setState。

较好：

能拆 Repository 和 Bloc。

优秀：

会讨论业务边界、部分失败、刷新策略、缓存、请求并发和状态粒度。

2. 搜索框连续请求如何优化

场景

用户输入：

B
Bl
Blu
Blue
Bluet
Blueto
Bluetooth

现在每输入一个字符就产生一次后端请求。

怎么办？

参考答案

至少应该考虑：

输入
 ↓
debounce
 ↓
取消旧请求
 ↓
只处理最后一次有效结果

在 BLoC 中可以采用：

SearchChanged
      ↓
debounce / restartable
      ↓
Repository.search()

关键不是简单加 300～500ms 延迟，而是解决请求乱序返回问题。

例如：

请求 A：blue        → 800ms 返回
请求 B：bluetooth   → 200ms 返回

如果 B 先返回、A 后返回，而业务没有取消或版本控制，页面最终可能展示旧的 blue 结果。

使用 Dio 时可考虑

  • CancelToken；
  • requestId；
  • BLoC restartable；
  • Repository 层统一取消上一次搜索；
  • 结果版本号校验。

面试关注点

看候选人是否真正处理过：

  • debounce；
  • 取消请求；
  • 异步乱序；
  • 输入快速变化；
  • 页面销毁后的返回结果。

3. Repository 是否只是 API 的包装层

场景

候选人写：

class UserRepository {
  Future<User> getUser() {
    return userApi.getUser();
  }
}

问：

如果 Repository 全是这种代码，它还有必要存在吗？

参考答案

如果 Repository 永远只是机械转发 API，价值确实有限。

真正有意义的 Repository 应该屏蔽数据来源与数据策略：

                 ┌── Remote API
UserRepository ──┼── Local DB
                 └── Memory Cache

例如：

Future<User> getUser() async {
  final cache = await local.getUser();

  if (cache != null && !cache.expired) {
    return cache;
  }

  final dto = await api.getUser();
  final user = mapper.toDomain(dto);

  await local.save(user);

  return user;
}

Repository 应该关注：

数据从哪里来
什么时候请求
什么时候缓存
如何转换
失败怎么处理

加分点

候选人如果能进一步谈到以下问题，说明架构经验较好：

  • DTO 与 Domain Model 分离；
  • 缓存策略；
  • stale-while-revalidate；
  • 离线数据；
  • API 与本地数据库融合；
  • Repository 接口方便 mock / test。

4. 项目到处直接使用 flutter_blue_plus，如何支持鸿蒙

场景

当前代码大量直接调用：

FlutterBluePlus.startScan();

散落在：

HomePage
BluetoothPage
DevicePage
SettingPage

现在要求支持：

Android + iOS + HarmonyOS

怎么改？

参考答案

不能继续让业务层依赖具体插件。

应该增加平台能力抽象层：

abstract interface class BluetoothService {
  Stream<BluetoothDevice> scan();

  Future<void> connect(String id);

  Future<void> disconnect(String id);

  Future<List<int>> read(...);

  Future<void> write(...);
}

Android / iOS：

BluetoothService
      ↑
FlutterBlueBluetoothService

鸿蒙：

BluetoothService
      ↑
HarmonyBluetoothService

业务层：

BluetoothBloc
      ↓
BluetoothRepository
      ↓
BluetoothService

最终：

                   ┌ FlutterBlue 实现
Bloc → Repository → BluetoothService
                   └ Harmony 实现

本质是：

业务依赖抽象，不依赖具体平台插件。

继续追问

如何处理平台能力不完全一致？

可以在接口层体现 capability：

abstract class BluetoothCapabilities {
  bool get supportsMtuChange;
  bool get supportsBackgroundScan;
  bool get supportsPhyUpdate;
}

不要让业务代码到处写：

if (Platform.isAndroid) ...

5. Flutter 页面滚动掉帧如何排查

场景

一个车辆列表：

500 条车辆
每条：
图片 + 状态 + 位置 + 5 个字段

滑动明显卡顿。

候选人说：

我会加 const。

这个答案够吗？

参考答案

不够。

正确的第一步应该是：

先 Profile，再优化。

不要直接猜。

排查思路：

DevTools Performance
        ↓
是 UI Thread？
        ↓
还是 Raster？
        ↓
找到耗时 Frame
        ↓
定位 Widget / Layout / Paint

进一步检查：

  • 是否使用 ListView.builder；
  • 图片尺寸是否过大；
  • build 执行次数；
  • Bloc 是否导致整页刷新；
  • 是否存在复杂嵌套布局；
  • IntrinsicWidth / IntrinsicHeight；
  • 大量 Opacity / Clip；
  • Shader；
  • Platform View；
  • JSON / 数据计算占用主 isolate。

继续追问

如果每收到一条车辆状态更新，500 个 item 全部 rebuild 怎么办？

可以考虑：

BlocSelector
buildWhen
拆小 Widget
按 vehicleId 选择状态

目标从：

VehicleBloc 变化
 ↓
500 item rebuild

优化为：

Vehicle #32 状态变化
 ↓
只刷新 VehicleItem #32

判断候选人水平

一般： 只会说 const、ListView.builder。
较好： 会谈 rebuild、图片和 DevTools。
优秀： 会区分 UI / Raster / Layout / Paint，并给出验证方法。

6. 20MB JSON 解析导致 UI 卡顿怎么办

场景

接口返回一个约 20MB JSON。

网络请求完成后，UI 明显卡住一段时间。

怎么办？

参考答案

首先要明确：

网络 IO 本身未必是瓶颈，真正卡顿的可能是 CPU 解析。

链路：

HTTP 返回
 ↓
20MB JSON decode
 ↓
Model 转换
 ↓
大量对象创建
 ↓
占用主 isolate

如果确定属于 CPU 密集型任务，可以考虑：

final result = await Isolate.run(() {
  return parseLargeJson(json);
});

继续追问

所有 JSON 都应该放 isolate 吗？

不应该。

因为 isolate 本身存在：

  • 调度成本；
  • 消息传递成本；
  • 数据跨 isolate 传输成本。

几十 KB 的普通 JSON 为了“优化”强行开 isolate，可能得不偿失。

优秀回答

候选人应该先：

  1. Profile；
  2. 判断真正耗时点；
  3. 确认解析是否阻塞主 isolate；
  4. 再决定是否使用 isolate。

7. Android 有能力而 iOS 没有，Flutter API 怎么设计

场景

Android 支持读取某车辆硬件状态，而 iOS 系统根本没有对应接口。

是否应该在业务代码里到处：

if (Platform.isAndroid) {
  ...
}

参考答案

不推荐。

应该通过 Capability / Service 抽象：

业务层
 ↓
Capability Interface
 ↓
Platform Implementation

例如：

abstract class VehicleHardwareService {
  bool get supported;

  Future<VehicleStatus?> getStatus();
}

Android：

class AndroidVehicleHardwareService
    implements VehicleHardwareService {

  @override
  bool get supported => true;
}

iOS：

class IOSVehicleHardwareService
    implements VehicleHardwareService {

  @override
  bool get supported => false;
}

业务层依赖统一抽象，而不是依赖平台判断。

加分点

如果候选人提到以下内容可加分：

  • capability discovery；
  • feature flag；
  • graceful degradation；
  • Platform Channel；
  • federated plugin；
  • 平台实现注册机制。

8. BLE 扫描页面退出后仍持续收到结果，怎么排查

场景

进入：

BluetoothPage

开始扫描。

退出页面后日志仍不停打印设备。

重新进入页面：

每台设备打印两遍。

第三次进入：

每台设备打印三遍。

为什么？

参考答案

首先怀疑：

StreamSubscription 没有取消。

例如：

subscription = bluetooth.scanResults.listen(...);

页面或 Bloc dispose 后没有：

await subscription.cancel();

还应该检查：

  • Bloc 生命周期管理错误；
  • BluetoothService 被重复初始化；
  • EventChannel 重复监听；
  • 原生 Listener 没有 unregister；
  • Scan 没有 stop；
  • Singleton 与页面级对象生命周期冲突；
  • 页面退出后 Bloc 是否仍存在。

优秀回答

更好的设计是：

BluetoothService
   ↓
统一管理扫描生命周期

而不是让每个页面直接控制底层 Bluetooth Plugin。

9. Android 11 能扫描 BLE，Android 13 却不能，怎么查

场景

同一个 Flutter App：

  • Android 11 正常扫描；
  • Android 13 扫描不到设备。

你会怎么排查？

参考答案

第一反应不应该是：

flutter_blue_plus 有 Bug。

应该先检查：

targetSdk
Android OS Version
Manifest
Runtime Permission
Bluetooth Adapter State
定位 / 附近设备权限

Android 12 以后蓝牙权限模型发生明显变化，需要针对新系统处理附近设备相关权限。

架构上应该有：

BluetoothPermissionService
        ↓
根据 OS Version
        ↓
选择权限策略

而不是权限逻辑散落在页面。

面试关注点

真正做过 BLE 的开发人员通常会优先检查：

权限
OS Version
Adapter State
Scan Lifecycle
原生日志

而不是先升级插件。

10. Flutter App 扫描 Wi‑Fi 并连接车机热点，如何设计

场景

App 需要：

  1. 扫描附近 Wi‑Fi；
  2. 找到指定车机热点；
  3. 连接热点；
  4. 建立后续 TCP / HTTP 通信。

怎么设计？

参考答案

不要让业务直接依赖某个 Wi‑Fi Plugin。

先定义统一接口：

abstract class WifiService {
  Future<List<WifiDevice>> scan();

  Future<WifiConnectResult> connect(
    WifiDevice device,
  );

  Stream<WifiState> observeState();
}

业务架构：

WifiBloc
   ↓
WifiRepository
   ↓
WifiService
   ↓
Android / iOS / Harmony

关键判断

Wi‑Fi 不是一个真正意义上“同一套 Flutter API 就能完全跨平台”的能力。

底层受到：

  • 系统权限；
  • API 限制；
  • 用户确认机制；
  • Wi‑Fi 扫描限制；
  • 后台限制；
  • OS 版本差异；

等影响。

因此正确思路是：

Android：实现 A
iOS：实现 B
Harmony：实现 C

Flutter 业务统一看到：
WifiService

加分点

候选人如果能主动提到：

  • iOS 无法像 Android 一样随意扫描附近 Wi‑Fi；
  • 系统设置跳转；
  • SSID 获取限制；
  • Android Nearby Wi‑Fi 权限；
  • 连接失败与网络切换回调；

说明跨平台经验较真实。

11. BLE 配网后切换 Wi‑Fi 通信，如何设计状态机

场景

设备配网流程：

扫描 BLE
 ↓
连接设备
 ↓
发送 Wi‑Fi SSID / Password
 ↓
设备加入 Wi‑Fi
 ↓
手机连接设备 Wi‑Fi
 ↓
切换 TCP / HTTP 通信

怎么设计？

参考答案

不建议堆大量嵌套：

if (...) {
  if (...) {
    if (...) {
      ...

建议明确状态机：

Idle
 ↓
Scanning
 ↓
BleConnecting
 ↓
BleConnected
 ↓
SendingWifiConfig
 ↓
WaitingDeviceNetwork
 ↓
WifiConnecting
 ↓
NetworkConnected
 ↓
Ready

任何状态还可能进入：

Failure
Disconnected
Timeout
Cancelled

BLoC 很适合表达这种业务：

Event
 ↓
ProvisionBloc
 ↓
State

底层：

               BluetoothService
              /
ProvisionRepo
              \
               WifiService

优秀候选人应该进一步考虑

  • 超时；
  • 用户取消；
  • 蓝牙断开；
  • Wi‑Fi 密码错误；
  • App 切后台；
  • 页面退出；
  • 重试；
  • 状态恢复；
  • OS 权限被拒绝；
  • BLE / Wi‑Fi 回调乱序；
  • 重复进入流程；
  • 幂等处理。

这是一道很适合高级 Flutter 工程师的题。

12. 蓝牙每秒上报 100 条数据，页面越来越卡，怎么解决

场景

BLE 每秒：

100 message/s

当前链路：

Bluetooth Plugin
 ↓
Stream
 ↓
Bloc.add()
 ↓
emit()
 ↓
BlocBuilder
 ↓
整个页面 rebuild

运行一段时间后页面越来越卡。

怎么办？

参考答案

不能简单回答：

用 isolate。

第一步应该拆解瓶颈：

BLE IO
 ↓
数据解包
 ↓
业务计算
 ↓
状态合并
 ↓
UI 刷新

1. 数据层

原始数据和 UI 状态分开。

100Hz BLE Raw Data
        ↓
Data Processor
        ↓
业务状态

不要让每个底层 packet 都直接驱动 UI。

2. CPU 层

如果协议解析、校验、算法计算很重，可以评估 isolate。

重点是：

isolate 用于 CPU 密集型工作，不是为了把所有异步代码都“多线程化”。

3. 状态层

不要每个 packet 都：

emit(...)

可以做聚合、采样或节流：

BLE：100 Hz
 ↓
数据聚合
 ↓
State：10 Hz
 ↓
UI：10 Hz

4. UI 层

将刷新粒度拆细：

车辆速度 → 速度 Widget
电量     → 电量 Widget
GPS      → 地图数据

可考虑：

  • BlocSelector；
  • buildWhen；
  • ValueNotifier；
  • 局部高频状态对象；
  • CustomPainter；
  • 避免整页 rebuild。

高级回答的关键点

优秀候选人通常会主动说：

UI 刷新频率不应该等于底层采样频率。

例如：

采集：100Hz
业务计算：50Hz
UI：10～30Hz

这是非常有区分度的一道 Flutter 性能 + 架构综合题。

13. 建议的面试组合与评分方式

如果技术面只有 40～60 分钟，不建议把 12 题全部问完。

推荐选择以下 6 道：

题目主要判断能力建议分值
首页三个接口怎么设计BLoC / Repository 架构15
搜索连续请求异步、并发控制10
flutter_blue_plus 如何支持鸿蒙跨平台架构20
500 条列表掉帧怎么查Flutter 性能15
Android 13 BLE 扫描失败原生平台能力15
BLE 100Hz 导致 UI 卡顿综合工程能力25

总分：100 分

推荐判断标准

60 分以下

更偏页面开发，对工程化和架构理解不足。

60～75 分

能够独立完成常规 Flutter 业务模块。

75～85 分

具备较好的工程设计和问题定位能力，可以承担核心模块。

85 分以上

具备高级 Flutter / 跨平台客户端工程师能力，可以参与架构设计、性能治理和平台能力抽象。

面试官重点观察

不要只看候选人是否“答出关键字”，更应该观察他有没有主动讨论：

  • 生命周期；
  • 异步乱序；
  • 超时与取消；
  • 状态恢复；
  • 平台差异；
  • 权限变化；
  • 原生层定位；
  • 数据采样频率；
  • UI 刷新频率；
  • 服务抽象；
  • Repository 边界；
  • 可测试性；
  • 可维护性；
  • 异常与降级。

真正做过复杂 Flutter 项目的人，回答通常不会停留在：

Bloc
Repository
const
ListView.builder
MethodChannel

而是会继续解释：

为什么这样设计、异常怎么处理、生命周期怎么管、平台差异怎么隔离、性能如何验证。
