Flutter实践类问题

八月 12, 2026 HEIN

一、工程与架构类

1. 一个页面同时需要“用户信息 + 车辆信息 + 消息列表”，你会怎么组织？

场景

现在有一个首页：

HomePage
 ├─ 用户信息
 ├─ 车辆信息
 └─ 消息列表

三个接口互相独立，但页面需要同时展示。你会怎么设计 Bloc、Repository 和页面状态？

参考答案

不建议在 HomePage 中直接写三个 Dio 请求，也不建议做一个巨大的 HomeRepository.getAll() 把所有业务绑死。

可以根据业务生命周期拆成：

HomePage
   │
   ├── UserBloc ─────→ UserRepository
   │
   ├── VehicleBloc ──→ VehicleRepository
   │
   └── MessageBloc ──→ MessageRepository

如果三个数据确实构成一个明确的“首页聚合业务”，也可以：

HomeBloc
   │
   ├── UserRepository
   ├── VehicleRepository
   └── MessageRepository

关键不是“一定几个 Bloc”，而是看状态生命周期和业务边界。Flutter 官方当前架构建议同样强调职责分离、数据层作为数据访问和更新的重要边界，而不是让 View 直接承担业务数据逻辑。(Flutter 文档)

继续追问

三个请求里一个失败了怎么办？

优秀回答应该提到：

不能简单只有：

Loading
Success
Failure

而应该允许部分成功，例如：

class HomeState {
  final User? user;
  final Vehicle? vehicle;
  final List<Message> messages;

  final LoadStatus userStatus;
  final LoadStatus vehicleStatus;
  final LoadStatus messageStatus;
}

判断候选人水平

一般：

Future.wait 三个接口，然后 setState。

较好：

能拆 Repository 和 Bloc。

优秀：

会讨论业务边界、部分失败、刷新策略、缓存、请求并发和状态粒度。

二、状态管理实战

2. 搜索框每输入一个字符都会请求后端，怎么优化？

场景

用户输入：
B
Bl
Blu
Blue
Bluet
Blueto
Bluetooth

现在产生 9 次请求。

怎么办？

参考答案

至少应该考虑三个问题：

输入
 ↓
debounce
 ↓
取消旧请求
 ↓
只处理最后一次有效结果

例如 BLoC 中：

SearchChanged
      ↓
restartable / debounce
      ↓
Repository.search()

关键不是简单加 500ms 延迟，而是解决旧请求比新请求晚回来的问题。

例如：

请求 A：blue        → 800ms 返回
请求 B：bluetooth   → 200ms 返回

B先返回
A后返回

如果没有请求序列控制，最终 UI 可能展示旧的 blue 结果。

继续追问

如果使用 Dio 怎么做？

可以：

  • CancelToken；
  • requestId；
  • BLoC restartable；
  • Repository 层取消上次查询。

这是非常实用的一道题，能迅速看出候选人有没有处理过真实异步业务。

三、Repository 设计

3. Repository 是不是简单把 Dio API 再包一层？

场景

候选人写：

class UserRepository {
  Future<User> getUser() {
    return userApi.getUser();
  }
}

问：

如果 Repository 全是这种代码，它还有必要存在吗？

参考答案

这种 Repository 的价值确实有限。

真正有意义的 Repository 应该屏蔽数据来源和策略，例如：

                 ┌── Remote API
UserRepository ──┼── Local DB
                 └── Memory Cache

例如：

Future<User> getUser() async {
  final cache = await local.getUser();

  if (cache != null && !cache.expired) {
    return cache;
  }

  final dto = await api.getUser();

  final user = mapper.toDomain(dto);

  await local.save(user);

  return user;
}

Repository 关注的是：

数据从哪里来
什么时候请求
什么时候缓存
如何转换
失败怎么处理

Flutter 官方当前架构文档同样把 data layer 视为应用数据的 source of truth，并建议把数据访问职责与 UI 分离。(Flutter 文档)

四、架构演进题

4. 项目现在到处直接使用 flutter_blue_plus，准备支持鸿蒙，怎么办？

场景

当前代码：

FlutterBluePlus.startScan();

分散在：

HomePage
BluetoothPage
DevicePage
SettingPage

现在要求：

Android + iOS + HarmonyOS。

你会怎么改？

参考答案

首先不能继续让业务依赖具体插件。

增加平台能力抽象层：

abstract interface class BluetoothService {

  Stream<BluetoothDevice> scan();

  Future<void> connect(String id);

  Future<void> disconnect(String id);

  Future<List<int>> read(...);

  Future<void> write(...);
}

Android/iOS：

BluetoothService
      ↑
FlutterBlueBluetoothService

鸿蒙：

BluetoothService
      ↑
HarmonyBluetoothService

业务层：

BluetoothBloc
      ↓
BluetoothRepository
      ↓
BluetoothService

最终：

                   ┌ FlutterBlue实现
Bloc → Repository → BluetoothService
                   └ Harmony实现

这实际上就是 Dependency Inversion。

Flutter 官方也建议插件通过平台实现与 Dart API 解耦；Flutter 的插件机制本身就是通过平台特定实现连接系统能力。(Flutter 文档)

这道题对你们这种需要考虑鸿蒙/Android 的项目很有区分度。

五、性能排查

5. Flutter 页面滚动明显掉帧，你第一步做什么？

场景

一个车辆列表：

500 条车辆
每条：
图片 + 状态 + 位置 + 5个字段

滑动明显卡顿。

候选人说：

我会加 const。

这个答案够吗？

参考答案

不够。

优秀候选人首先应该说：

先 profile，再优化。

而不是先猜。

Flutter 官方当前性能指南也强调性能优化首先应该基于可测量指标，并使用 DevTools Performance View 等工具定位问题。(Flutter 文档)

排查：

DevTools Performance
        ↓
是 UI Thread？
        ↓
是 Raster？
        ↓
找到耗时 Frame
        ↓
定位 Widget / Layout / Paint

再检查：

ListView.builder
图片尺寸
build执行次数
Bloc刷新范围
复杂布局
IntrinsicWidth/Height
Opacity
Clip
Shader
PlatformView
JSON解析

Flutter 官方性能建议特别提醒避免不必要的 expensive operations 和过度复杂的 build/layout。(Flutter 文档)

继续追问

如果每收到一条车辆状态更新，500 个 item 全部 rebuild 怎么办？

比较好的回答：

BlocSelector
buildWhen
拆小 Widget
按 vehicleId 做状态选择

目标是：

以前：
VehicleBloc变化
 ↓
500 item rebuild

优化：
Vehicle #32发生变化
 ↓
只刷新 VehicleItem #32

六、CPU 密集型任务

6. 接口返回 20MB JSON，解析时 UI 卡住，怎么办？

参考答案

网络请求本身不是关键问题。

真正的问题可能是：

HTTP返回
 ↓
20MB JSON decode
 ↓
Model转换
 ↓
大量对象创建
 ↓
占用主 isolate

这类 CPU 密集任务可以考虑放到 isolate。

例如：

final result = await Isolate.run(() {
  return parseLargeJson(json);
});

Flutter / Dart 官方建议在计算量足以阻塞其他工作、导致 UI 无响应时使用 isolate。(Flutter 文档)

陷阱

问：

那所有 JSON 都放 isolate 好不好？

正确答案：

不好。

因为 isolate：

  • 有创建/调度成本；
  • 有消息传递成本；
  • 数据需要跨 isolate 传输。

几十 KB JSON 没必要为了“优化”硬开 isolate。

七、跨平台架构题

7. Android 有一个能力，iOS 没有，Flutter API 怎么设计？

场景

例如：

Android：
支持读取某车辆硬件状态

iOS：
系统根本没有这个接口

是不是应该：

if (Platform.isAndroid) {
   ...
}

到处判断？

参考答案

不推荐。

应该：

业务层
 ↓
Capability Interface
 ↓
Platform Implementation

例如：

abstract class VehicleHardwareService {

  bool get supported;

  Future<VehicleStatus?> getStatus();
}

Android：

class AndroidVehicleHardwareService
    implements VehicleHardwareService {

  @override
  bool get supported => true;
}

iOS：

class IOSVehicleHardwareService
    implements VehicleHardwareService {

  @override
  bool get supported => false;
}

这样业务代码不会到处：

if (Platform.isAndroid)

Flutter 官方 Platform Channel 就是 Dart 与 Kotlin/Swift 等平台代码通信的标准机制。(Flutter 文档)

八、蓝牙实战题

8. BLE 扫描页面退出以后，还一直收到扫描结果，怎么排查？

场景

进入：

BluetoothPage

开始扫描。

退出页面以后日志仍然不停打印设备。

重新进页面以后：

每台设备打印两遍。

第三次进去：

打印三遍。

为什么？

参考答案

典型问题：

Stream subscription 没有取消。

例如：

subscription =
    bluetooth.scanResults.listen(...);

页面/Bloc dispose 时没有：

await subscription.cancel();

还可能存在：

  • Bloc 生命周期管理错误；
  • BluetoothService 被重复初始化；
  • EventChannel 重复监听；
  • 原生 listener 未 unregister；
  • scan 没调用 stop；
  • 全局 singleton 和页面级 Bloc 生命周期混用。

优秀候选人还应该提出：

扫描状态最好由 BluetoothService
统一管理，而不是页面控制底层生命周期

九、Android 蓝牙权限题

9. Android 11 能扫描 BLE，升级到 Android 13 后突然不能扫描，怎么查？

参考答案

第一反应不应该是：

flutter_blue_plus 有 bug。

应该先看：

targetSdk
Android版本
Manifest
Runtime Permission
蓝牙状态
定位/附近设备权限

Android 12 / API 31 开始采用新的 Bluetooth runtime permissions，包括扫描/连接等附近设备权限；旧版蓝牙权限需要兼容处理。(Android Developers)

所以需要做按 OS Version 的权限策略：

Android <= 11
       ↓
旧权限逻辑

Android >= 12
       ↓
BLUETOOTH_SCAN
BLUETOOTH_CONNECT
...

这道题看什么？

如果候选人的第一反应永远是：

升插件。

通常说明原生 Android 基础偏弱。

真正做过 BLE 的开发人员，一般首先检查：

权限
OS Version
Adapter State
Scan Lifecycle
原生日志

十、Wi-Fi 实战题

10. Flutter App 想扫描附近 Wi-Fi，然后连接某个车机热点，怎么设计？

参考答案

不要让业务直接依赖某一个 Wi-Fi plugin。

应该先定义业务接口：

abstract class WifiService {

  Future<List<WifiDevice>> scan();

  Future<WifiConnectResult> connect(
    WifiDevice device,
  );

  Stream<WifiState> observeState();
}

然后：

WifiBloc
   ↓
WifiRepository
   ↓
WifiService
   ↓
Android / iOS / Harmony

而且需要认识到：

Wi-Fi 并不是一个真正“一套 Flutter API 就可以完全跨平台”的能力。

底层权限、安全限制和可调用 API 都受 OS 控制。Android 13 及以上针对附近 Wi-Fi 设备引入了 NEARBY_WIFI_DEVICES runtime permission，并保留了旧版本的兼容权限策略。(Android Developers)

所以正确架构应该允许：

Android：实现 A
iOS：实现 B
Harmony：实现 C

但 Flutter 业务看到：
WifiService

十一、蓝牙 + Wi-Fi 综合题

11. 设备通过 BLE 配网，最终切换到 Wi-Fi 通信，怎么设计状态机？

这是我比较推荐拿来面高级 Flutter 的一道题。

场景

智能设备配网：

扫描 BLE
 ↓
连接设备
 ↓
发送 Wi-Fi SSID / Password
 ↓
设备加入 Wi-Fi
 ↓
手机连接设备 Wi-Fi
 ↓
切换 TCP / HTTP 通信

怎么设计？

参考答案

不建议：

if (...) {
  if (...) {
     if (...) {

建议明确状态机：

Idle
 ↓
Scanning
 ↓
BleConnecting
 ↓
BleConnected
 ↓
SendingWifiConfig
 ↓
WaitingDeviceNetwork
 ↓
WifiConnecting
 ↓
NetworkConnected
 ↓
Ready

同时任何状态都可能进入：

Failure
Disconnected
Timeout

BLoC 非常适合表达这种业务：

Event
 ↓
ProvisionBloc
 ↓
State

底层：

               BluetoothService
              /
ProvisionRepo
              \
               WifiService

优秀候选人应该进一步考虑

  • 超时；
  • 用户取消；
  • 蓝牙断开；
  • Wi-Fi 密码错误；
  • App 切后台；
  • 页面退出；
  • 重试；
  • 恢复上次状态；
  • OS 权限被拒绝；
  • BLE 和 Wi-Fi 回调乱序。

如果能主动谈到这些，基本可以判断做过复杂设备连接类业务。

十二、最有区分度的一道性能 + 架构综合题

12. 蓝牙每秒上报 100 条数据，页面越来越卡，怎么解决？

场景

BLE：

100 message/s

每条消息：

Bluetooth Plugin
 ↓
Stream
 ↓
Bloc.add()
 ↓
emit()
 ↓
BlocBuilder
 ↓
整个页面 rebuild

运行几分钟以后明显卡顿。

怎么处理？

参考答案

不能简单回答：

用 isolate。

首先判断瓶颈在哪。

整个链路拆开：

BLE IO
 ↓
数据解包
 ↓
业务计算
 ↓
状态合并
 ↓
UI刷新

IO 不一定是问题。

真正问题通常可能是：

100次/s Event
100次/s emit
100次/s rebuild

优化方向：

数据层

把原始数据和 UI 数据分开。

100Hz BLE Raw Data
        ↓
Data Processor
        ↓
业务状态

CPU 层

复杂解析/算法必要时放 isolate。Dart 官方建议 isolate 用于可能阻塞 UI isolate 的计算密集型工作。(Dart)

状态层

不应该每个 packet 都：

emit(...)

可以：

BLE：100 Hz
 ↓
聚合
 ↓
State：10 Hz
 ↓
UI：10 Hz

UI 层

例如：

车辆速度 → 只刷新速度Widget
电量 → 只刷新电量Widget
GPS → 只刷新地图数据

使用：

BlocSelector
buildWhen
ValueNotifier（局部高频状态）
CustomPainter

很优秀的回答

候选人会主动说：

UI 的刷新频率不应该等于底层数据采样频率。

例如传感器：

采集：100Hz
业务：50Hz
UI：10~30Hz

这是我认为这组题里区分度最高的一题。

面试时我建议这样组合

如果只安排 40～60 分钟技术面，其实不需要问几十道题。我会挑下面 6 道核心题：

题目主要判断能力建议分值
首页三个接口怎么设计BLoC / Repository 架构15
搜索连续请求异步、并发控制10
flutter_blue_plus 如何支持鸿蒙跨平台架构20
500条列表掉帧怎么查Flutter 性能15
Android 13 BLE 扫描失败原生平台能力15
BLE 100Hz 导致 UI 卡顿综合工程能力25

其中最后一道可以直接作为高级 Flutter 工程师分水岭。

一个候选人如果能够把：

BLE 100Hz
→ 数据处理层
→ Repository
→ Bloc状态聚合
→ UI低频刷新
→ isolate处理CPU密集计算
→ BlocSelector控制局部重建

这条链路完整说清楚，基本可以判断他不只是“会 Flutter”，而是具备真正的跨平台客户端工程设计能力。Flutter 官方当前也明确将 isolate 用于计算密集型任务，并建议性能问题先基于 DevTools 和实际指标定位，而不是凭感觉优化。(Flutter 文档)
