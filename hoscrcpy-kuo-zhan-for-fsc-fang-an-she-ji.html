HOScrcpy 扩展 for FSC 方案设计

十月 15, 2026 HEIN

设计一套通用的进程型扩展机制，HOScrcpy 只是第一个实现，而不是在 FSC 内部增加大量鸿蒙专用分支。

核心边界是：

  • 主程序负责扩展管理、标准协议、设备展示、媒体解码和通用交互。
  • 扩展包负责 SDK、设备通信、平台命令、运行时及系统差异。
  • 现有 Android 链路保留，首期不进行全项目后端重构。

下面是一份可用于后续实施评审的详细设计。本次仍未修改代码，也未执行实机验证。

1. 当前状态与设计目标

1.1 当前已经具备什么

当前仓库版本为 2.6.3+263，工作区干净。上一轮鸿蒙接入方案尚未实施。

已有基础可以如何复用仍然缺少什么
FFmpeg 视频解码与 macOS Texture 显示接收扩展输出的标准视频数据SDK 字节流到完整编码包的适配
DecodedVideoFrame、VideoDecoder共用媒体显示边界独立于 Android 页面的显示组件
文件名、保存位置、大小格式化等公共服务扩展截图、下载等功能复用扩展文件安装与版本管理
UpdateService 流式下载与进度反馈提取公共下载基础设施签名、解压、自检、回滚、卸载
设置页紧凑表单组件扩展设置及安装界面扩展参数描述与权限提示
设备与镜像生命周期管理经验参考状态机、引用计数设计与 Android 无关的扩展会话管理

当前 DeviceProvider 依赖 ADB，MirrorSessionProvider 保存 FScrcpyClient，MirrorPage 也直接使用 Android 控制接口。因此它们还不是通用设备后端接口。

相关代码：设备管理、镜像会话、镜像页面。

1.2 本次设计的约束

  1. FSC 安装包不包含 HOScrcpy、HDC、JRE 或鸿蒙设备端库。
  2. 用户从 APP 内显式安装扩展后，才具有对应能力。
  3. 扩展更新尽量不要求更新 FSC。
  4. Android 既有行为、性能和配置不受影响。
  5. 后续其他系统可以使用同一套扩展管理和通信协议。
  6. 不追求首期实现任意第三方代码、任意 UI、任意原生插件的动态加载。

这里的“改动最小”应理解为尽量不侵入 Android 业务链，而不是完全零改动。安全下载、运行管理和公共协议必须由主程序提供。

2. HOScrcpy 的实际支持边界

2.1 本地 SDK 基线

已核对你提供的实际文件：

  • SDK：hosScrcpy-1.0.18-beta.jar。
  • 大小：约 17.6 MiB。
  • libs 下标为 1.0.14 的文件与其哈希相同，属于文件名与实际内容不一致。
  • 公开 API 的字节码版本为 Java 8；Manifest 的构建环境为 JDK 21。
  • SDK 内含 gRPC、Guava、JSON 等依赖。
  • SDK 内没有 JavaCV/FFmpeg；这些属于示例程序额外引入的依赖。
  • 支持视频流、图片流、触摸、鼠标、分辨率缩放、帧率/码率设置、显示屏设置、关键帧请求。
  • 公开 API 未提供音频流和双向剪贴板接口。

因此扩展不应携带原始 Swing 示例，更不需要再装一套 JavaCV 解码链路。

依据：项目说明、[API 文档](<C:/TEMP/HOScrcpy-main/hoscrcpy API介绍.md>)、示例依赖。

2.2 电脑端桌面平台

必须区分“有接入基础”和“已经实测支持”。

电脑端平台静态分析结论发布建议
Windows x64上游提供使用说明；可采用 x64 JRE、HDC，复用 FSC 解码首批验证平台
macOS Intel x64上游明确提供 macOS 使用说明和对应依赖首批验证平台
macOS Apple Silicon ARM64项目 POM 包含 ARM64 依赖；Java SDK 本身具备跨架构基础首批验证平台，但不能仅凭 POM 宣称已验证
Linux x64FSC 和 HDC 有平台基础；上游 README 未提供完整 Linux 示例构建说明实验支持，验证 SDK 运行后再开放
Windows ARM64当前 FSC 运行时、FFmpeg、HDC 分发链未完整覆盖首期不支持
Linux ARM64同样缺少已验证的 FSC 媒体和工具分发组合首期不支持
鸿蒙电脑作为 FSC 宿主属于新的应用宿主平台适配不由本扩展自动解决

HDC 官方文档确认其支持 Windows、Linux、macOS，并指出独立运行时可能需要随带 libusb_shared，不能只复制一个 hdc 文件。HDC 官方文档

结论：首批目标是 Windows x64、macOS ARM64/x64；Linux x64作为验证后开放的平台。本次没有跨平台实测，不能把这些候选平台标为“已验证支持”。

2.3 被投屏设备的架构

JAR 内 .so 是推送到鸿蒙设备执行的，不是电脑端加载的 JNI 库。

被投屏设备当前 SDK 包的基础应如何处理
ARM64 鸿蒙 NEXT 真机视频采集库均为 ARM64核心接入目标，仍需核对系统/内核兼容性
ARM64 鸿蒙模拟器有 ARM64、带 emulator 名称的采集库候选支持，需验证实际模拟器系统
x86_64 鸿蒙模拟器视频采集库仍是 ARM64；输入代理包含 x86_64 版本不能承诺视频模式；验证图片流兜底
ARM32 设备未发现相应视频采集库不支持
OpenHarmony 开发板CPU 相同不代表系统 ABI、权限和服务都兼容按具体系统单独认证
鸿蒙电脑作为被投屏端不能从手机支持情况直接推导单独验证，不默认开放

具备 ADB/Android 兼容能力的旧款华为设备，仍优先使用现有 Android 后端，不要根据品牌自动选择 HOScrcpy。

SDK 中有按内核版本区分的采集库，但这不等于支持所有相应内核或所有鸿蒙版本。最终兼容性应记录为：

SDK 版本 + HDC 版本 + 设备型号/架构 + 系统构建号 + 视频/控制模式。

3. 总体架构

建议分成四个边界：

层职责是否随 FSC 安装
扩展宿主安装、校验、版本、进程、协议连接是
通用设备与镜像 UI展示设备、播放媒体、发送标准交互是
系统适配扩展发现、连接、控制、媒体采集适配否，按需下载
设备端代理由对应扩展通过合法通道部署和管理否，包含在扩展中或由设备自身提供

鸿蒙链路为：

FSC 通用扩展客户端
  ↕ 本机标准 IPC
鸿蒙桥接服务
  ├─ HDC：设备发现、连接、命令执行
  └─ HOScrcpy：采集和反向控制
       ↕
     鸿蒙设备

视频进入 FSC 后：

H.264 字节流 → 分帧适配 → 现有 FFmpeg → 共用画面组件
JPEG 图片   → 图片解码 → 共用画面组件

这里“Java”只是鸿蒙扩展的实现语言，不是插件规范的一部分。未来插件可以使用 Rust、C++、C#、Go 等，只要提供兼容的进程和协议即可。

4. 主程序接口设计

4.1 核心对象

建议新增以下中立对象，避免使用 adbSerial、Android KeyCode 等平台概念：

对象核心内容
ExtensionDescriptorID、版本、平台、协议范围、运行入口、声明能力
ExtensionRuntime进程启动、鉴权、连接、健康检查、退出
DeviceDescriptor后端 ID、设备唯一键、名称、系统、连接方式、状态
DeviceCapabilities设备此时实际可用的能力
MirrorSession会话状态、媒体流、输入控制、停止
DisplayDescriptor显示屏 ID、原始尺寸、旋转、编码尺寸
ExtensionError错误码、阶段、详情、可重试性

设备标识采用结构化形式：

extensionId + backendId + endpointId + opaqueDeviceId

其中 opaqueDeviceId 对宿主是不透明的。主程序不能根据冒号、前缀或名称猜测设备类型。

4.2 最小标准方法

扩展协议首版需要明确支持：

  • 扩展：hello、health、shutdown。
  • 设备：devices.list、devices.watch、devices.getCapabilities。
  • 会话：sessions.open、sessions.close、sessions.configure。
  • 媒体：streams.requestKeyFrame。
  • 控制：input.pointer、input.scroll、input.key、input.text。

连接、文件、应用、日志等作为可选接口，不要求每个插件实现。

宿主必须区分：

  • 不支持。
  • 支持但未获授权。
  • 当前设备不可用。
  • 暂时失败。

不能把它们统一当作“执行失败”。

4.3 能力协商

能力在三个层级确定：

  1. 安装包声明“这个扩展可能提供什么”。
  2. 运行时报告“当前平台能提供什么”。
  3. 设备/会话报告“当前目标实际能提供什么”。

最终可用能力取宿主理解范围和上述能力的交集。

例如鸿蒙会话：

{
  "mirror.video": true,
  "mirror.image": true,
  "input.touch": true,
  "input.mouse": true,
  "input.text": false,
  "audio.capture": false,
  "clipboard.read": false,
  "clipboard.write": false,
  "recording.encoded": false
}

能力可以在运行中变化，例如授权撤销、显示屏断开、视频模式降级。UI 应响应能力变化，而不是只在页面创建时读取一次。

5. 扩展包与版本规范

5.1 包结构

以鸿蒙为例：

harmony-mirror/<version>/
├─ manifest.json
├─ bridge/
│  └─ fsc-hos-bridge.jar
├─ sdk/
│  └─ hosScrcpy-1.0.18-beta.jar
├─ runtime/
│  └─ 对应平台的私有 Java 运行时
├─ tools/
│  └─ HDC 及必要依赖
└─ licenses/

同一个 JAR 可以进入多个平台包，但 JRE、HDC、系统依赖必须匹配平台。

不依赖系统 JAVA_HOME，不要求用户修改 PATH。私有运行时版本固定并经过测试；首期可选择经过验证的 JRE 21组合，而不是同时支持任意系统 Java。

5.2 三种版本分别管理

版本用途
扩展包版本更新整个可运行组件
IPC/API 版本判断是否能和主程序通信
SDK/HDC/JRE 版本设备兼容、安全维护和故障定位

SDK 升级不应自动等于协议升级。

协议采用“主版本 + 次版本”：

  • 主版本不兼容：拒绝启动并提示升级。
  • 次版本新增可选能力：通过协商使用。
  • 新增未知字段：忽略。
  • 未知方法：返回标准“不支持”。
  • 禁止在同一主版本下改变已有字段含义。

5.3 清单与下载目录

发布清单至少包含：

  • 扩展 ID、发布者、包版本。
  • 主程序兼容范围、协议范围。
  • OS、CPU 架构和必要系统依赖。
  • 下载大小、解压大小上限、SHA-256。
  • SDK/HDC/JRE 版本。
  • 签名、签名密钥 ID。
  • 发布通道、撤回/停用信息。

签名应覆盖版本、平台、哈希等关键元数据。只提供 HTTPS 和哈希不足以建立独立的发布信任链。

首期建议仅接入官方维护的扩展目录，不直接开放任意第三方扩展市场。

6. 安装、更新、停用与卸载

6.1 本地目录

使用应用用户数据目录，不修改 FSC 安装目录或 macOS .app：

extensions/
├─ registry.json
├─ staging/
└─ harmony-mirror/
   ├─ versions/
   ├─ data/
   ├─ cache/
   └─ logs/

版本目录安装后保持只读式使用；配置、缓存、日志不写进去。

6.2 安装事务

流程为：

  1. 获取匹配平台且兼容的版本。
  2. 用户确认下载和所需访问范围。
  3. 下载到唯一临时目录。
  4. 校验签名、文件哈希、大小。
  5. 防护解压路径穿越、符号链接逃逸、解压炸弹。
  6. 检查可执行文件和平台架构。
  7. 执行不连接设备的自检与协议握手。
  8. 原子切换活动版本。

任何一步失败都不影响已安装版本。

既有 UpdateService 仅提供部分下载基础，不应把其临时安装器目录和启动安装程序逻辑直接套用于扩展。现有实现

6.3 更新与回滚

  • 正在使用的会话固定到启动时的扩展版本。
  • 新包可以后台下载，但默认在会话结束后激活。
  • 保留上一可用版本。
  • 新版本启动失败可回退；设备不兼容则提示选择已认证版本。
  • 被明确撤回的安全问题版本不能静默回退。
  • 断网时已安装扩展仍能使用。
  • 主程序升级或降级后，重新判断协议兼容性。

6.4 停用与卸载

停用：停止发现和会话，不再启动进程，保留配置。

卸载：先停止自己的工作进程和端口转发，再删除版本文件。用户数据、日志、认证信息是否清理需单独选择，不能默认删除已有 DevEco/HDC 的认证材料。

7. 运行进程与通信协议

7.1 鸿蒙进程模型

首期推荐：

  • 一个扩展管理进程：设备发现、HDC 配置、工作进程管理。
  • 每个活动投屏设备一个 SDK 工作进程。

这样能够隔离设备故障，也避免闭源 SDK 内部状态和端口互相影响。

代价是多 JVM 会增加内存占用。需要设置并发上限并测量实际资源，再决定是否合并工作进程；不能预先保证多设备内存很小。

7.2 启动握手

  1. 宿主使用扩展目录内的绝对路径启动运行时。
  2. 随机鉴权信息通过标准输入等受控通道传入，不放在命令行参数或 URL。
  3. 服务绑定 127.0.0.1 的动态端口。
  4. Bootstrap 通道返回端口、协议和进程信息。
  5. 宿主连接并鉴权，完成版本及能力协商。
  6. 成功后才允许设备操作。

SDK 普通日志必须与 Bootstrap/协议输出隔离，宿主持续消费 stdout、stderr，避免堵塞进程。

不要沿用示例中的固定 8899、全局 remoteDevice 和 broadcast()。示例代码

7.3 控制与媒体

首版采用本机 WebSocket：

  • JSON-RPC 风格消息：请求、响应、错误和事件。
  • 二进制消息：视频、图片及未来音频。
  • 所有请求有 ID、超时和取消语义。
  • 启动/停止请求应可重复处理，避免重试产生重复会话。
  • 会话与流分别编号，不能通过当前全局设备推断消息归属。
  • 未鉴权连接、异常 Origin、超大消息应拒绝。

二进制协议建议使用固定头部，至少包含：

协议版本、消息类型、流 ID、序列号、时间戳、标志位、负载长度。

媒体格式要明确区分：

  • H.264 Annex-B 字节流块。
  • H.264 Annex-B 完整访问单元/编码包。
  • JPEG/PNG 图片。
  • 后续协商支持的其他格式。

不能只写一个含义不明的 video。

8. 视频、时间戳与输入细节

8.1 H.264 适配

HOScrcpy 的 ByteBuffer 不是已证明一包一帧的数据。

项目示例调用 av_parser_parse2，而 FSC 当前 feed() 接口直接向解码器提交编码包。因此需新增独立的流适配器，处理：

  • 跨回调拆包和粘包。
  • SPS/PPS、IDR 检测及缓存。
  • 分辨率变化、旋转、解码重建。
  • 断流后的缓存清理。
  • 队列积压和关键帧恢复。

当前各平台 FFmpeg 构建脚本已启用 H.264 parser，但 Dart FFI 尚需增加对应绑定；应验证实际随包库的导出和行为，而非仅依赖编译脚本文字。

依据：HOScrcpy 示例、FSC 解码绑定。

8.2 时间戳与录制

SDK 公开回调没有直接提供逐帧 PTS。

因此：

  • 协议必须允许“时间戳未知”，不能把零或到达时间冒充设备采集时间。
  • 直播显示可采用经过验证的播放节奏策略。
  • 录制需要另行解决逐帧时间和可变帧率问题。
  • 不能因为能解码 H.264，就直接宣布 MP4 录制已支持。

后续若增加录制，优先让一次采集同时服务预览和录制，不默认再开一个 SDK 采集连接。关闭预览仅取消显示订阅，录制仍持有采集引用。

8.3 图片流与首帧

  • 图片与状态消息先识别再解码。
  • 静止画面保持最后一帧，不按“长时间没帧”直接判定断线。
  • onReady 和收到首帧是两个状态。
  • 视频解码器就绪后请求 IDR。
  • 超时提供重新请求或图片模式降级。
  • 不通过偷偷注入触摸、电源键来触发首帧。

图片流的刷新频率和静止补帧效果仍需按设备验证。

8.4 输入模型

宿主发送语义操作，扩展负责系统映射：

  • 指针按下、移动、抬起、取消。
  • 鼠标按钮及滚轮。
  • 返回、主页、音量等语义按键。
  • 文本提交。

同时协商原始设备尺寸、编码尺寸、旋转及坐标空间。输入必须绑定当前显示屏和画面版本，旋转时取消旧手势。

移动事件可以合并，按下/抬起/取消不能丢失。失焦、断线时释放按键和指针，避免设备残留“按住”状态。

文本输入应做转义、长度和字符范围处理。不能把用户文本直接拼接为 shell 命令，也不能沿用 Android KeyCode 数值。

9. HDC 专项设计

HDC 自身也有客户端、电脑端服务器和设备端守护进程。

必须区分：

  • HDC 服务端地址。
  • 设备 target key。
  • 无线设备 IP/端口。

hdc -s 指向电脑端 HDC 服务，tconn 才是连接网络设备，二者不能共用一个模糊的“IP”字段。官方说明

建议：

  • 默认使用扩展包内固定版本 HDC。
  • 检测已有 DevEco 服务，检查版本和兼容性。
  • 必要时使用应用管理的独立服务端口。
  • 记录自己创建的转发和进程，只清理自己拥有的资源。
  • 不执行全局杀进程、全局重置 HDC 来修复单设备问题。
  • 设备扫描可见时正常刷新，隐藏或空闲时降低频率。
  • 未启用扩展时不扫描、不启动 HDC。

同时测试 Windows 驱动、Linux USB 权限、macOS 本地网络授权，以及路径中包含空格和中文的情况。

10. 对现有代码的具体改动范围

建议沿用上一方案的旁路策略，但新增页面应做成通用扩展页面，而不是鸿蒙专用页面。

现有位置拟改动Android 影响控制
main.dart注册扩展状态、增加路由/入口不改变原 Android Provider 初始化语义
设备页增加设备来源切换，原 Android 内容继续使用鸿蒙不进入现有 ADB 刷新和名称查询
设置页增加扩展管理卡片或独立管理页既有偏好不迁移
mirror_page.dart 的纯显示部分抽取共用画面组件原输入、UHID、剪贴板逻辑保留
FFmpeg bindings增加 parser 绑定，独立流适配器调用不改变 Android 编码包路径
公共下载基础按需抽取下载/进度底层原主程序更新行为保持
macOS 配置与分发流程校验权限描述、辅助程序签名和公证作为跨平台发布专项验证
本地化与测试增加扩展状态、错误及能力提示保留现有回归套件

主要新增模块：

  • 扩展目录与安装器。
  • 扩展运行监督器和协议客户端。
  • 通用扩展设备 Provider。
  • 通用扩展会话 Provider。
  • 通用扩展设备页、镜像页和参数表单。
  • 鸿蒙 Java 桥接工程及能力包构建流水线。

首期扩展镜像可作为二级页面打开，避免立即重写现有按 Android serial 管理的投屏网格。

如果要求 Android、鸿蒙同时混排在同一投屏网格，应另做一次小范围路由改造，将槽位标识改为通用设备引用。不要把这项需求隐藏为“无需改动”。

11. UI 与配置扩展性

11.1 扩展管理

至少展示：

  • 未安装、下载中、校验中、已安装、启用、运行中。
  • 待激活更新、异常、与主程序不兼容。
  • 包版本、SDK 版本、平台和磁盘占用。
  • 安装、取消、重试、停用、更新、回滚、卸载。
  • “复制诊断信息”和查看日志。

错误详情保留原始 SDK/HDC 信息，但不显示令牌、认证密钥等敏感内容。

11.2 插件不直接注入 UI 代码

首版允许插件声明有限的表单：

  • 布尔值、数字、字符串、枚举。
  • 范围、默认值、说明和校验规则。
  • 设备选择、显示屏选择。
  • 标准动作及危险操作确认。

主程序用现有 Settings*Field 渲染，不执行插件提供的 HTML、JS、Dart 或任意 Widget。

这样新的投屏插件只需声明参数和能力，不必为每个系统新增专用设置页。

但边界也应明确：需要全新原生控件、特殊播放器或主程序尚不认识的媒体格式时，仍需升级宿主，不能无限依赖配置扩展。

12. 后续接入其他操作系统

插件接口应围绕“设备、流、输入、权限”，不能绑定 HDC 或 Java。

后续方向可选实现方式不能预设的能力
其他鸿蒙设备/SDK新后端或更新现有桥接不同设备、内核和权限不自动兼容
Android 其他投屏方案独立进程适配，未来也可包装现有 Android 后端不要求立即把现有 Android 功能插件化
iOS/iPadOS设备端发送应用、系统允许的采集框架，或获得授权的供应商 SDK不能默认支持全系统反控、USB 即插即用或无感授权
Windows 被控端远端采集代理或既有远程桌面协议适配采集授权、控制权限和安全桌面需单独处理
macOS 被控端远端代理使用系统采集能力屏幕采集与辅助控制权限分别管理
Linux 被控端X11/Wayland 对应采集与控制后端不能把 X11 行为直接套用于 Wayland
RDP/VNC 等协议扩展实现协议，再输出宿主支持的媒体与输入接口协议图形指令不能直接当 H.264 使用

Windows 提供 Windows.Graphics.Capture 等采集接口；Linux Wayland 可通过 ScreenCast/RemoteDesktop portal 协商画面和输入权限；Apple 平台需按目标系统版本选择采集框架并遵循用户授权。Windows 文档、XDG RemoteDesktop、Apple ScreenCaptureKit

需要特别区分：

桌面扩展包是接收端适配；某些系统还需要被控设备安装发送端/代理。扩展机制不会自动创造操作系统不允许的采集或控制能力。

对未来插件，媒体格式不匹配时有两个选择：

  1. 插件转换成宿主已有格式，独立更新即可，但可能增加延迟和资源消耗。
  2. 宿主增加新格式/原生通道支持，需要升级 FSC。

首期不建设动态加载第三方原生 DLL 的播放器机制。后续确有性能瓶颈，再设计共享内存、系统句柄或零拷贝传输，不能提前把不稳定的跨平台 ABI 固化为插件协议。

13. 安全、授权与发布维护

13.1 信任模型

首期建议只允许：

  • 官方维护并签名的在线包。
  • 使用同一信任体系签名的离线导入包。

第三方开发者模式单独设计，默认关闭。

**独立进程不是安全沙箱。**扩展以当前用户权限执行，声明“只访问设备”并不能从技术上阻止恶意进程读取用户文件。首期安全基础是可信发布者、签名校验、最小运行权限和明确用户授权，而非虚假的权限隔离承诺。

13.2 平台安全

  • macOS：扩展内 JRE、HDC、辅助可执行程序纳入签名、公证和本地网络权限验证，不要求用户关闭系统安全机制。Apple 分发要求
  • Windows：安装及运行不默认提权，进程树退出可采用 Job Object 等机制。
  • Linux：明确最低系统依赖和 USB 权限要求，不能简单承诺一个包适用全部发行版。
  • 本机 IPC 只监听回环地址，随机鉴权，拒绝任意网页调用。
  • 宿主退出、控制管道关闭、心跳丢失均应触发清理；不能只依赖可能被复用的 PID 判断父进程存活。

13.3 许可证与供应链

此次核对发现，JAR 内 META-INF/LICENSE.txt 对应 Checker Framework qualifiers，不能据此推定整个 HOScrcpy SDK 及设备端库都允许再分发。

公开发布前需要确认：

  • SDK JAR 与设备端库的再分发范围。
  • HDC、libusb 和 JRE 的分发要求。
  • 必须保留的许可证与声明。
  • 内嵌第三方依赖的 SBOM 和安全更新方式。

不能因为“扩展单独下载”就绕过授权问题。若暂未获得再分发确认，可设计用户导入合法取得的 SDK 模式，但不能视为全部合规问题已经解决。

14. 验证、发布顺序与最终边界

14.1 必须覆盖的测试

类别重点
安装事务断网、取消、磁盘不足、损坏包、错误平台、解压攻击、进程崩溃
协议版本不兼容、未知字段、错误长度、超大消息、未鉴权连接
视频拆包粘包、静止首帧、SPS/PPS、旋转、尺寸改变、积压、关键帧恢复
输入缩放映射、旋转、越界、失焦释放、中文和特殊字符
生命周期反复开关、拔线、SDK 卡死、父进程退出、双设备隔离
共存DevEco Studio、不同 HDC 版本、Android 投屏同时运行
跨平台Windows x64、macOS ARM64/x64，Linux x64独立验证
回归未装扩展时，原 Android 行为与性能保持

平台和设备兼容性测试结果形成版本化清单。不得根据 Java 能启动或 hdc list targets 成功就标记“投屏已支持”。

14.2 实施阶段

  1. P0：许可与 PoC
    确认分发范围，验证 ARM64 真机视频、图片模式、输入、关键帧、多设备及退出清理。

  2. P1：最小扩展宿主
    安装、校验、进程、协议、通用扩展设备页和镜像页。首先交付 USB 投屏与基础控制。

  3. P2：产品化
    跨平台认证、自动更新/回滚、诊断、网络连接和远程 HDC，按验证结果增加截图与录制。

  4. P3：多系统扩展
    用第二种非鸿蒙后端检验协议通用性，再决定是否统一 Android 设备列表和混合投屏网格。

最终应形成的产品边界是：

FSC 内置一个轻量、稳定的投屏扩展宿主；鸿蒙 SDK、HDC、JRE 和适配逻辑由能力包独立分发。以后新增系统，只要能使用既有设备、媒体和控制契约，就可以独立安装和更新；超出契约的能力再通过宿主升级扩展，而不破坏已有插件。
